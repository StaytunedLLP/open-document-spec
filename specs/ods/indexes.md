# ODS · Indexes

How navigation indexes are structured, how the workspace boundary is declared, and how tools scan a tree.

Root keys dictionary: [keys.md](keys.md) §4.

---

## 1. Progressive disclosure

Index files provide hierarchical navigation: start at the root index, descend one directory level at a time, load only documents along the path.

### 1.1 Placement and filename

- **Preferred filename:** `index.ods.md` (sidecar that leaves SSG `index.md` free when both exist).
- Tools MUST also accept `index.md` as a workspace/index document for compatibility.
- A **root** index with scalar `ods:` (e.g. `ods: 0.1`) marks the workspace boundary. There is no separate manifest file.
- Any directory MAY have its own index.
- An index MUST list only **immediate** children (documents and subdirectories). Nested navigation belongs in child indexes.

### 1.2 Content

An index is a Markdown list of links, each with an optional one-line summary:

```markdown
---
profile: index
---

# Product Documentation

- [features/](features/index.ods.md) - customer-facing capabilities
- [api/](api/index.ods.md) - HTTP API reference
- [architecture.md](architecture.md) - system overview and trade-offs
```

Rules:

- Indexes MUST NOT contain document counts, size statistics, or other metadata that requires an update on every commit.
- Indexes SHOULD be generated by tooling (`ods index`) and treated like lockfiles—reviewed and committed, not hand-edited for child lists. Summaries SHOULD come from each child's frontmatter `description`.
- `status` is optional on indexes and usually omitted.
- The **root** index MUST declare the ODS workspace marker once:

```yaml
---
profile: index
ods: 0.1
custom-profiles:
  - docs/profiles/rfc.md
packs:
  - vendor/engineering-pack
ignore:
  - src
---
```

### Dual-scope governance

1. **Machine level (`~/.ods/odsconfig.toml`)** — registry of workspace paths for the background service (`ods start`). Legacy `~/.ods/odcconfig.toml` MAY still be read.
2. **Repository level (root index frontmatter)** — policy lives on the root index only: `ods:`, `custom-profiles:` / legacy `profiles:`, `packs:`, `ignore:`, `aliases:`, `specs:`. ODS enforces a **zero in-repo config-file guarantee** (no required `.odsconfig` / `.odsignore` inside the project).

Ordinary documents MUST NOT declare the workspace marker `ods: 0.1`. Nested indexes SHOULD omit root-only keys.

## 2. Scan ignore defaults

Tools that walk a workspace MUST NOT treat these directory **base names** as documentation content (case-insensitive): `target`, `node_modules`, `dist`, `build`, `.artifacts`, `.git`, `.hg`, `.svn`, `.jj`, `__pycache__`, `.venv`, `venv`, `vendor`, and any name starting with `.`.

The root index MAY add workspace-relative path prefixes under `ignore:`:

```yaml
---
profile: index
ods: 0.1
ignore:
  - src
  - apps/web
---
```

Each entry is a path prefix. Tools MUST NOT collect Markdown under those prefixes, MUST NOT require indexes there, and MUST NOT list ignored trees as index children.

Tools MAY also respect `.gitignore`. ODS does **not** define a separate ignore file format for project policy.

Index child validation SHOULD consider only top-level Markdown list links (unordered list items with a single link), not every prose link.
